# repo-radar — Technical Design

**Status:** Draft v1
**Last updated:** 2026-09-02
**Companion to:** [PRD.md](PRD.md) — this document assumes the PRD's requirements and does not restate them. Where a section implements a specific requirement, it cites the FR number.

---

## 1. Design overview

The PRD describes *what* repo-radar does. This document specifies *how*: module boundaries, domain types, the database schema, the algorithms that carry the most risk, and the contracts between the Rust core and the React frontend.

Three decisions shape everything else:

1. **The analysis core is a plain Rust library with no Tauri dependency.** Everything — discovery, parsing, OSV ingestion, matching, scoring — lives in a `repo-radar-core` crate that can be exercised from `cargo test` with no GUI, no webview, and no app shell. `src-tauri` is a thin adapter that owns state, exposes commands, and emits events. This is the single most important structural choice in the project: the parts most likely to be wrong (lockfile parsers, version-range matching) are also the parts that must be testable in isolation.

2. **Advisory matching is two-phase: SQL narrows, Rust decides.** SQLite cannot evaluate a SemVer range or a PEP 440 ordering. So the database narrows candidates by exact `(ecosystem, package_name)` join — cheap, indexed, high-selectivity — and the version-interval decision happens in Rust with the correct comparator per ecosystem. §8.4 specifies this.

3. **One writer, many readers.** Parallel repo analysis produces values, not database writes. Analysis threads send `RepoAnalysis` over a channel to a single writer thread that batches into transactions. This sidesteps SQLite write contention entirely rather than managing it.

### 2.1 Why one core crate rather than four

An earlier sketch split `parsers`, `osv`, and `db` into separate crates. One crate with modules is better here: the boundaries are identical, but moving a type across a module boundary is free while moving it across a crate boundary means editing two `Cargo.toml` files and often introducing a third crate for shared types. Compile time is the only argument for splitting, and it does not bite at this size. Revisit if core exceeds ~15k lines or clean builds exceed ~90s.

## 3. Layering rules

| Layer | May depend on | Must not depend on |
|-------|--------------|-------------------|
| `core::model` | serde, chrono | anything else in core |
| `core::version`, `core::parsers` | `model` | `db`, `osv::sync`, `scan` |
| `core::osv::matcher` | `model`, `version` | `db` (takes candidates as arguments) |
| `core::db` | `model` | `scan`, `parsers`, `osv::sync` |
| `core::scan` | everything in core | `src-tauri` |
| `src-tauri` | `core` | — |

Two rules are load-bearing:

- **`core` never depends on `tauri`.** Filesystem paths arrive via an injected `Paths` struct (§13.1); progress is reported through a `ScanReporter` trait (§6.4) that `src-tauri` implements with event emission and tests implement with a `Vec`.
- **`osv::matcher` never touches the database.** It is a pure function from `(dependency, candidate advisories)` to findings. This is what makes the highest-risk algorithm in the project testable from hand-written fixtures (§16.2).

### 4.1 The `Warning` type

Per FR-1.10, FR-4.8, and §15, *nothing in a scan is fatal at the scan level*. Every recoverable problem becomes a `Warning`:

```rust
pub struct Warning {
    pub scope: WarningScope,        // Scan | Repo(id) | File(path)
    pub kind: WarningKind,          // PermissionDenied | ParseFailed | GitTimeout | ...
    pub message: String,
}
```

Warnings are persisted with the scan and surfaced in the UI. A repo that produced warnings is badged, and the badge is clickable. Silent degradation is the failure mode to avoid: a repo whose lockfile failed to parse must not look identical to a repo with no vulnerabilities.

## 5. Persistence

### 5.1 Connection strategy

SQLite in WAL mode. One dedicated **write** connection behind a `Mutex`, owned by the writer thread; a small **read** pool (`r2d2_sqlite`, 4 connections) for queries serving the UI. WAL lets readers proceed during writes, which matters because a scan writes continuously while the user browses already-completed repos.

Pragmas set on every connection:

```sql
PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;      -- durability tradeoff acceptable: this is a rebuildable cache
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 5000;
```

`synchronous = NORMAL` is deliberate. Every byte in this database is derived — from the user's repos or from OSV — and can be regenerated by re-scanning. Trading crash-durability for write throughput is the right call here and would not be in an app holding original user data.

### 5.2 Migrations

Sequential numbered SQL files embedded with `include_str!`, applied in order, tracked in a `schema_version` table. No ORM, no migration framework. Down-migrations are not supported; the recovery path for a corrupt or incompatible database is **Reset database** (FR-10.3), which is acceptable for derived data.

## 6. Scan pipeline

### 6.1 Orchestration

```rust
pub fn run_scan(
    ctx: &ScanContext,             // db handles, rule packs, paths
    roots: &[ScanRoot],
    cancel: &CancelToken,
    reporter: &dyn ScanReporter,
) -> Result<ScanSummary>
```

Runs on a blocking thread (`spawn_blocking` from the Tauri side) because the work is CPU- and IO-bound, not async-bound. Rayon provides parallelism inside.

### 6.2 Stages

```
  [1] discover        single-threaded walk per root (ignore crate, internally parallel)
        ↓ Vec<RepoIdentity>
  [2] analyze         rayon par_iter over repos — the parallelism unit is one repo
        │   git metadata (git2)      ─┐
        │   language stats (tokei)    ├─ independent, run sequentially within a repo
        │   manifest discovery        │
        │   dependency parsing       ─┘
        │   technology rules
        │   categorization
        ↓ RepoAnalysis, sent over mpsc as each completes
  [3] persist         single writer thread, batched transactions
        ↓
  [4] match + score   after persistence, per repo (§8.4, §9)
        ↓
  [5] emit            scan:repo_done per repo, scan:complete at the end
```

Stage 2 sends each `RepoAnalysis` to the writer as soon as it is ready; the UI sees repos appear progressively rather than in one batch at the end (Journey A).

### 6.3 Cancellation

`CancelToken` wraps `Arc<AtomicBool>`. Checked at three points: between discovery batches, at the top of each repo's analysis, and in the writer loop. Because the granularity is one repo, worst-case cancellation latency equals the slowest single repo's analysis — bounded by the git timeout in FR-7.10. Meets the 1s target in §11 of the PRD for all realistic repos.

Cancellation is not an error. Results already persisted stay; the scan record is marked `cancelled`.

### 6.4 Progress reporting

```rust
pub trait ScanReporter: Send + Sync {
    fn discovered(&self, total: usize);
    fn repo_done(&self, summary: &RepoSummary);
    fn warning(&self, w: &Warning);
    fn finished(&self, summary: &ScanSummary);
}
```

`src-tauri` implements this by emitting events (§12.2). Tests implement it by pushing to a `Mutex<Vec<_>>`. This is the seam that keeps `core` free of Tauri.

### 6.5 Incremental re-scan (FR-5.6 / PRD §7.6)

A repo's `scan_fingerprint` is:

```
blake3( head_sha ‖ Σ sorted(manifest_path ‖ content_hash) ‖ rule_pack_version )
```

If the fingerprint is unchanged, stages 2 and 3 are skipped and the stored analysis is reused.

**Stage 4 always runs regardless of fingerprint.** This is the crux of Journey B: the advisory database changes independently of the code, so a repo nobody touched can become unhealthy. Skipping the match step for unchanged repos would defeat the product's central purpose. Fingerprinting is an optimization for *parsing*, never for *matching*.

Including `rule_pack_version` in the fingerprint means editing a rule file correctly invalidates every repo's classification.

### 6.6 Discovery algorithm (FR-1)

```
for each enabled root:
    WalkBuilder::new(root)
        .hidden(false)             # .git is hidden; we need to see it
        .follow_links(false)       # FR-1.8
        .git_ignore(false)         # we are above the repo level; repo gitignores
                                   # do not apply to finding repos
        .filter_entry(prune list)  # FR-1.4
    on directory entry:
        if entry contains ".git":
            record repo
            skip descending           # FR-1.3
        continue
```

`.git` may be a directory (normal), or a file containing `gitdir:` (worktree, FR-1.7). Both are handled by delegating to `git2::Repository::open` and letting libgit2 resolve it; if it errors, the candidate is recorded as a warning rather than silently dropped.

Submodules (FR-1.5) are read from the parent's `.gitmodules` after the parent opens. Because the walker stops descending at the parent, submodules are never independently discovered — they are attached as children explicitly. Their dependencies are inserted with the *parent's* `repo_id` so they roll into the parent's health.

## 7. Dependency parsers

### 7.1 The trait

```rust
pub trait LockfileParser: Send + Sync {
    fn ecosystem(&self) -> Ecosystem;
    fn kind(&self) -> ManifestKind;                 // Lockfile | Manifest
    fn matches(&self, path: &Path) -> bool;         // by file name
    fn parse(&self, content: &str, path: &RelPath) -> Result<Vec<Dependency>, ParseError>;
}
```

Parsers are registered in a `Vec<Box<dyn LockfileParser>>`. Adding Java/.NET/PHP/Ruby later (PRD N7) means implementing this trait and adding an `Ecosystem` variant — no change to the pipeline, matcher, or scorer.

### 7.2 Selection rule

Per repo, per manifest directory: if any lockfile parser matches a present file, use it and mark all its output `Confidence::Exact`. Otherwise fall back to the manifest parser and mark output `Confidence::Range` (FR-4.2). Both may run when the manifest is needed to determine *directness* — see below.

### 7.3 Per-format notes

**`package-lock.json`** — v2/v3 use the `packages` map keyed by path (`""` is the root, `node_modules/foo` is a dependency). v1 uses nested `dependencies`. Support both; detect by `lockfileVersion`. Directness comes from the root entry's `dependencies`/`devDependencies` keys, not from tree position.

**`pnpm-lock.yaml`** — YAML via `serde_yaml`. The `importers` section gives directness per workspace package; `packages` gives the resolved set. Keys are of the form `/foo@1.2.3` or `/@scope/foo@1.2.3`; parsing must split on the *last* `@` to handle scoped names.

**`yarn.lock`** — v1 is a bespoke non-YAML format requiring a hand-written parser. Berry (v2+) is YAML-ish. Per PRD R2: implement v1 first; if berry proves costly, treat berry repos as manifest-confidence with a visible notice rather than shipping a half-correct parser. A wrong version string produces a wrong finding, which is worse than an honest "unconfirmed".

**`Cargo.lock`** — TOML, `[[package]]` array. Trivial. Directness from `Cargo.toml` `[dependencies]` / `[dev-dependencies]` / `[build-dependencies]`, which also supplies `Scope`.

**`go.mod` / `go.sum`** — Per PRD R6, `go.sum` is **not** the dependency set. It contains hashes for modules considered during resolution, often multiple versions of the same module, including ones not in the final build. The design: **`go.mod`'s `require` block determines the build list; `go.sum` only confirms versions.** Using `go.sum` as the inventory would systematically over-report. Indirect requires are marked `is_direct = false` via the `// indirect` comment.

**Python** — `poetry.lock` and `uv.lock` are TOML and give exact versions. `Pipfile.lock` is JSON. `requirements.txt` is exact **only if every line is pinned with `==`** (FR-4.9); a mixed file is manifest-confidence throughout, because partial trust is not expressible in the model and defaulting to trust would be wrong.

### 7.4 Name normalization (FR-4.5)

Applied identically to `dependencies.name` and `affected_ranges.package_name`, so the join in §8.4 is a plain equality. This function is the single point where a mismatch silently produces false negatives, so it is unit-tested against a table of known cases per ecosystem.

| Ecosystem | Rule |
|-----------|------|
| PyPI | Lowercase; collapse runs of `-`, `_`, `.` to a single `-` (PEP 503) |
| npm | Lowercase; preserve `@scope/` prefix verbatim |
| crates.io | Lowercase; `-` and `_` are **distinct** — do not collapse |
| Go | Verbatim, case-sensitive, including `/v2` major suffixes |

The crates.io rule is a deliberate exception to the pattern; collapsing `-`/`_` there would merge genuinely different crates.

## 8. OSV ingestion and matching

This section covers the highest-risk logic in the project.

### 8.1 Record subset

Only the fields needed are deserialized; unknown fields are ignored so schema additions do not break ingestion.

```rust
#[derive(Deserialize)]
pub struct OsvRecord {
    pub id: String,
    pub modified: String,
    pub published: Option<String>,
    pub withdrawn: Option<String>,
    pub aliases: Option<Vec<String>>,
    pub summary: Option<String>,
    pub details: Option<String>,
    pub severity: Option<Vec<OsvSeverity>>,
    pub affected: Option<Vec<OsvAffected>>,
    pub references: Option<Vec<OsvReference>>,
    pub database_specific: Option<serde_json::Value>,
}

#[derive(Deserialize)]
pub struct OsvAffected {
    pub package: OsvPackage,                 // { ecosystem, name, purl }
    pub ranges: Option<Vec<OsvRange>>,       // { type, events[] }
    pub versions: Option<Vec<String>>,       // explicit enumeration
    pub ecosystem_specific: Option<serde_json::Value>,
    pub database_specific: Option<serde_json::Value>,
}
```

**Withdrawn advisories are excluded from matching** but retained in the table, so a finding that disappears can be explained rather than just vanishing.

### 8.2 Classifying compromise vs vulnerability (FR-6.1)

```rust
fn classify(record: &OsvRecord) -> FindingKind {
    if record.id.starts_with("MAL-") { return FindingKind::Compromise; }
    if record.aliases.iter().flatten().any(|a| a.starts_with("MAL-")) {
        return FindingKind::Compromise;
    }
    // OpenSSF Malicious Packages records carry a malicious-code marker in
    // database_specific; treat it as authoritative when present.
    if has_malicious_marker(&record.database_specific) { return FindingKind::Compromise; }
    FindingKind::Vulnerability
}
```

Per PRD R1, the exact shape of the `database_specific` marker and the per-ecosystem coverage of `MAL-` IDs **must be verified against a live snapshot during M2 before UI is built on top of it.** `has_malicious_marker` is deliberately isolated as one small function so that verification changes one place. If an ecosystem turns out to have thin `MAL-` coverage, the UI must say so for that ecosystem rather than implying a clean bill of health.

#### 8.2.1 M2-12 spike findings (verified against a live OSV snapshot, 2026-09-02)

Enumerated every object in `gs://osv-vulnerabilities/{ecosystem}/` and fetched
a sample of `MAL-` records per ecosystem.

**Record shape — consistent across all four ecosystems.** A `MAL-` record has:

- `id` of the form `MAL-YYYY-NNNN` — always. This alone is a reliable classifier.
- Top-level `database_specific["malicious-packages-origins"]` — a **non-empty
  array** on every `MAL-` record. Each entry carries `source` (`ghsa-malware`,
  `ossf-package-analysis`, `google-open-source-security`, `checkmarx`, …),
  `sha256`, `import_time`, `modified_time`, and optionally `id`, `ranges`,
  `versions`. **This is the marker** `has_malicious_marker` checks: the key is
  present and the array is non-empty.
- `affected[].package` — **always present and usable**: `{ name, ecosystem,
  purl }`. The name maps straight onto a normalized dependency name.
- Version spec in one of two forms (sometimes both on one record):
  - `affected[].ranges` = `[{ type: SEMVER|ECOSYSTEM, events: [{introduced:"0"}] }]`
    — "every version affected", no `fixed`. Typical for typosquats / removed packages.
  - `affected[].versions` = `["1.0.0"]` — explicit single version. Typical for
    OpenSSF Package Analysis detections. **The `affected[].versions[]` matching
    path (§8.4) is therefore mandatory for compromise detection, not optional.**
- `affected[].database_specific.cwes` — sometimes `CWE-506` ("Embedded Malicious
  Code"), present on GHSA-sourced records, absent on OpenSSF Package Analysis
  records. A weaker secondary signal; not needed given the `MAL-` prefix + origins array.
- **No `severity` field** on any `MAL-` record → they band as `Unscored`. Fine:
  compromise is a health *cap* (§9 step 2), not severity-driven.
- A few objects are truncated/error bodies (e.g. `PyPI/MAL-2024-1.json`). A
  `MAL-` record that fails to deserialize is logged and skipped, never fatal.

**Per-ecosystem `MAL-` coverage:**

| Ecosystem | Total OSV records | `MAL-` records | Assessment |
|-----------|------------------:|---------------:|------------|
| npm       | ~200,000          | ~192,700       | Comprehensive (dominated by automated OpenSSF/GHSA feeds) |
| PyPI      | ~25,300           | ~11,700        | Substantial |
| crates.io | ~2,800            | **19**         | **Thin** — spot reports only, no systematic automated feed |
| Go        | ~9,100            | **18**         | **Thin** — spot reports only, no systematic automated feed |

**Product decision (D1 outcome).** `classify()` and `has_malicious_marker` as
written are correct and need no change. But for **crates.io and Go**, "no
compromise findings" reflects ~18 monitored packages, not a systematic scan.
The core exposes a per-ecosystem `MalCoverage { Strong | Thin }` value
(`Thin` for crates.io and Go, `Strong` for npm and PyPI, hard-coded from this
spike and revisited each release). The Health tab, the Advisories screen, and
any "no compromises" empty state **must render the `Thin` caveat** for repos
whose dependencies are crates.io/Go — a clean result there is "we checked the
few known cases", not "this is clean".

### 8.3 Severity extraction

Precedence:

1. `severity[]` entry of type `CVSS_V4`, else `CVSS_V3` — parse the vector string with the `cvss` crate, take the base score, band it (`≥9.0` Critical, `≥7.0` High, `≥4.0` Medium, `>0` Low).
2. `database_specific.severity` string (GHSA supplies `CRITICAL`/`HIGH`/`MODERATE`/`LOW`) — map `MODERATE` → Medium.
3. `Severity::Unscored`, which carries its own deduction weight (FR-6.4) rather than being treated as harmless.

### 8.4 The matching algorithm

**Phase 1 — narrow (SQL).** For a repo, join its dependencies against advisory ranges on exact normalized name:

```sql
SELECT d.id, d.name, d.version, d.confidence, d.scope, d.is_direct,
       a.id, a.kind, a.severity, ar.range_type, ar.events
FROM dependencies d
JOIN affected_ranges ar
  ON ar.ecosystem = d.ecosystem AND ar.package_name = d.name
JOIN advisories a
  ON a.id = ar.advisory_id AND a.withdrawn IS NULL
WHERE d.repo_id = ?;
```

Plus the analogous query against `affected_versions`, where the version comparison *can* be done in SQL as exact string equality.

**Phase 2 — decide (Rust).** For each candidate range, evaluate whether the dependency's version falls inside an affected interval. OSV ranges are event lists, not intervals, and must be interpreted with this algorithm:

```rust
/// A version is affected by a range if, walking the range's events in
/// ascending version order and applying only those at or before the target,
/// the most recent applicable event left it in the "introduced" state.
fn is_affected(version: &Ver, range: &Range, scheme: &dyn VersionScheme) -> bool {
    let mut events: Vec<&Event> = range.events.iter().collect();
    events.sort_by(|a, b| scheme.cmp_event(a, b));   // "0" sorts as -infinity

    let mut affected = false;
    for e in events {
        match e {
            Event::Introduced(v)  if scheme.gte(version, v) => affected = true,
            Event::Fixed(v)       if scheme.gte(version, v) => affected = false,
            Event::LastAffected(v) if scheme.gt(version, v) => affected = false,
            _ => {}
        }
    }
    affected
}
```

An advisory affects a dependency if **any** of its ranges matches **or** the version appears in the explicit `versions[]` list.

Three traps this design guards against, each of which produces silent false negatives or false positives:

- A range with an `introduced` and no `fixed` means *everything from that version onward is affected*. Naive interval logic that requires an upper bound misses these entirely — and these are common for unpatched advisories.
- `last_affected` is inclusive; `fixed` is exclusive. Using `>=` for both is wrong in one direction.
- Events must be sorted with the **ecosystem's own comparator**, not lexically. Lexical sorting puts `1.10.0` before `1.9.0`.

### 8.5 Version schemes (FR-4.6)

```rust
pub trait VersionScheme: Send + Sync {
    fn parse(&self, s: &str) -> Result<Ver, VersionError>;
    fn cmp(&self, a: &Ver, b: &Ver) -> Ordering;
}
```

| Ecosystem | Scheme | Crate |
|-----------|--------|-------|
| npm, crates.io | SemVer | `semver` |
| PyPI | PEP 440 | `pep440_rs` |
| Go | Go module ordering (SemVer plus pseudo-version handling) | `semver` with a pre-normalization step stripping the `v` prefix |

These are **not** a shared code path. Comparing PyPI versions with SemVer would mis-order `1.0.0rc1`, `1.0.0.post1`, and epoch-prefixed versions, silently producing wrong findings — the kind of bug that looks like it works until it matters.

An unparseable version is **not** silently skipped. It produces a `Warning` and the dependency is marked as unmatchable in the UI, because "we could not check this" and "this is fine" must never look the same.

### 8.6 Sync implementation (FR-5)

**Full sync.** Stream the ecosystem zip with `reqwest`, feed to the `zip` crate, deserialize each entry, and insert in transactions batched at ~1,000 records. Per FR-5.10, the archive is never fully buffered — neither the zip bytes nor the deserialized set. Peak memory stays proportional to batch size, not to advisory count.

**Incremental sync.** Fetch `modified_id.csv`, read from the top (reverse chronological) until reaching an entry older than `last_successful_sync`, collect the IDs, then fetch each via `GET /v1/vulns/{id}` with bounded concurrency (8). If the delta exceeds 2,000 IDs, abandon and fall back to a full zip download — at that point the zip is cheaper than the individual requests.

**Atomicity.** Ingestion for one ecosystem runs in a transaction that replaces that ecosystem's ranges wholesale on full sync. A failed sync leaves the previous snapshot intact (FR-5.7); there is no partially-applied state.

**Retry.** Exponential backoff with jitter, capped at 5 attempts, then record the failure in `sync_log` and surface it. No tight retry loop.

## 9. Health scoring

Pure function, no IO, fully unit-testable:

```rust
pub fn score(findings: &[Finding], hygiene: &HygieneInputs, w: &Weights) -> HealthResult;

pub struct HealthResult {
    pub score: u8,
    pub band: Band,
    pub breakdown: Vec<Deduction>,   // serialized to repos.health_breakdown
    pub capped_by: Option<String>,
}

pub struct Deduction {
    pub cause: DeductionCause,       // links to advisory_id or a git fact
    pub label: String,
    pub amount: f32,
    pub multipliers: Vec<(&'static str, f32)>,  // ("dev scope", 0.5), ("range", 0.4)
}
```

Algorithm:

1. Start at 100.
2. **Compromise cap (FR-6.3).** If any finding is `Compromise` with `Confidence::Exact` and not suppressed → cap the final score at 39 and record `capped_by`. A cap, not a subtraction: a good score elsewhere must not be able to average away a backdoored package.
3. **Vulnerability deductions (FR-6.4).** Base by severity (Critical 15, High 8, Medium 3, Low 1, Unscored 2), then multipliers: `×0.4` for `Confidence::Range` (FR-6.5), `×0.5` for Dev/Build scope (FR-6.6).
4. **Diminishing returns per package.** Findings are grouped by `(ecosystem, name)`; within a group, deductions are sorted descending and scaled by `1 / (1 + index)`. One badly-maintained transitive dependency with twelve advisories contributes roughly its worst finding plus a tail, not twelve full deductions.
5. **Hygiene (FR-6.7).** No lockfile −5; no commit in 365d −5 or 730d −10 (not cumulative); dirty tree −2.
6. **Hygiene floor (FR-6.8).** Hygiene deductions in aggregate cannot take the score below 60. They signal neglect, not danger, and must never be able to masquerade as a security finding.
7. Clamp to `0..=100`, apply the cap, band it.

`Weights` is deserialized from a config file (FR-6.10) with the PRD's values as `Default`, not exposed in settings UI in phase 1.

`breakdown` is the serialized input to the UI's explainability view (FR-6.9). Because the UI renders this structure directly rather than recomputing anything, the number shown and the number explained cannot drift apart.

## 10. Rule packs

### 10.1 Format

```toml
# categories.toml
[[rule]]
id      = "react-frontend"
weights = { frontend = 5 }
any_dependency = ["react", "vue", "svelte", "@angular/core"]

[[rule]]
id      = "server-framework"
weights = { backend = 5 }
any_dependency = ["express", "fastify", "koa", "axum", "actix-web", "django", "fastapi", "gin-gonic/gin"]

[[rule]]
id      = "iac"
weights = { devops = 6 }
any_file = ["*.tf", "Chart.yaml", "kustomization.yaml", "ansible.cfg"]

[[rule]]
id      = "publishable-library"
weights = { library = 4 }
predicate = "has_manifest_without_entrypoint"   # named built-in predicate
```

Signal kinds: `any_dependency`, `all_dependencies`, `any_file` (glob), `any_language` (with an optional minimum percentage), and `predicate` (a small closed set of named built-ins). Arbitrary expressions are deliberately not supported — a rule DSL is a language, and a language needs a parser, error messages, and a debugger. The closed set covers the cases and stays diagnosable.

### 10.2 Loading and merging (FR-2.6, FR-3.8)

Shipped pack is `include_str!`-embedded. User pack at `<config>/rules/*.toml` is parsed separately and merged by rule `id`: same id replaces, new id appends. A malformed user pack produces a startup `Warning` and is ignored — the app continues with the shipped pack rather than failing to start.

`rule_pack_version` = hash of the effective merged pack, and it participates in the scan fingerprint (§6.5) so a rule edit correctly invalidates cached classifications.

### 10.3 Category resolution (FR-3.3 / 3.4 / 3.5)

Accumulate weights per category. Then:

- Top score below `floor` (default 3) → `Unknown` (FR-3.5). Guessing is worse than admitting ignorance.
- Top two are `Frontend` and `Backend`, both above `fullstack_threshold` (default 4), within `margin` → `Fullstack` (FR-3.4). This case is common and picking arbitrarily between them would be visibly wrong to the user.
- Otherwise, highest wins. Confidence from the margin: `>5` high, `>2` medium, else low.

The full per-rule and per-category breakdown is serialized to `repos.category_scores` for FR-3.6.

## 14. Frontend

### 14.1 Data flow

TanStack Query wraps every command. Tauri events invalidate query keys rather than pushing data into the cache directly — a single invalidation path is easier to reason about than two ways for data to arrive.

```
scan:repo_done  → invalidate ['repos']  and ['repo', id]
sync:complete   → invalidate ['repos'], ['syncStatus'], ['advisories']
```

Query keys: `['repos', filter]`, `['repo', id]`, `['syncStatus']`, `['settings']`, `['templates']`, `['outdated', repoId]`.

### 14.2 Structure

Feature-first, not type-first — `features/repos/`, `features/health/`, `features/prompts/`, `features/advisories/`, `features/settings/`, each owning its components, hooks, and types. Shared primitives live in `components/ui/` (shadcn). Grouping by feature keeps a change to the health view inside one directory instead of touching four parallel trees.

### 14.3 Notable components

- **`RepoTable`** — TanStack Table + `@tanstack/react-virtual`. Compromise and vulnerability counts render in separate columns with separate colors (FR-6.1); a single "issues" column would destroy the distinction the health model exists to make.
- **`HealthBreakdown`** — renders `health_breakdown` JSON directly. Because it displays the stored computation rather than recomputing, the explanation cannot drift from the score (FR-6.9).
- **`CompromiseBanner`** — rendered on the dashboard **only when compromise findings exist**. It must mean something when it appears; a banner that is always present is furniture.
- **`CategorySignals`** — the FR-3.6 breakdown, with the override control (FR-3.7) adjacent so correcting the classifier is a one-click action from the evidence that was wrong.
- **`FreshnessIndicator`** — global, always visible, escalating past 7 and 30 days (FR-5.6).

### 14.4 Empty and degraded states

Designed explicitly, not as an afterthought: no scan roots configured; scan running with no results yet; scan complete with zero repos found; advisory database never synced (health shown as *unknown*, **not** as healthy — this distinction is essential and must be visually unambiguous); network unavailable; repo with warnings.

## 15. Error handling

Three tiers:

| Tier | Handling |
|------|----------|
| **Recoverable, per-item** | Unreadable directory, unparseable lockfile, git timeout, unparseable version → `Warning`, recorded and surfaced, processing continues |
| **Recoverable, per-operation** | Sync failure, registry timeout → operation marked failed in its log table, previous state retained, user notified with a retry affordance |
| **Fatal** | Database corruption, migration failure → error screen offering **Reset database** and **Open data folder** |

Panics inside a single repo's analysis are caught at the repo boundary (`catch_unwind` around the per-repo closure) and converted to a `Warning`. One malformed lockfile triggering a panic in a parser must not take down a 50-repo scan.

## 16. Testing

### 16.1 Parser tests

Real lockfiles committed as fixtures under `crates/core/tests/fixtures/`, covering at minimum: npm v1/v2/v3, pnpm with workspaces, yarn v1, `Cargo.lock` with a workspace, `go.mod` with indirect requires, `poetry.lock`, `uv.lock`, pinned and mixed `requirements.txt`. Each asserts exact dependency count, a spot-check of names/versions, and correct direct/transitive and scope flags. Golden-file snapshots for the full output.

### 16.2 Matcher tests

The highest-value tests in the suite, built from hand-written OSV records rather than live data so they are deterministic and cover cases real data may not currently exhibit:

- `introduced` with no `fixed` (everything onward affected) — the case naive interval logic misses
- `last_affected` (inclusive) vs `fixed` (exclusive) boundary behavior
- Multiple disjoint ranges in one `affected` entry
- Explicit `versions[]` with no ranges
- Events requiring ecosystem-correct sorting (`1.9.0` vs `1.10.0`)
- PEP 440 specifics: `1.0.0rc1`, `1.0.0.post1`, epochs
- Withdrawn advisories excluded
- Name normalization round-trips per ecosystem (§7.4)

### 16.3 Scoring tests

Pure-function property tests: score always in `0..=100`; a confirmed compromise always yields `band == Critical` regardless of other inputs; hygiene-only deductions never produce a score below 60 (FR-6.8); breakdown amounts sum to `100 - score` when no cap applied.

### 16.4 The read-only invariant

An integration test that builds a fixture repo tree, records a hash of every file's content and mtime, runs a full scan, and asserts nothing changed. Principle 4 is a promise to the user about their source code; it needs a test, not just an intention.

### 16.5 Integration

`tempdir` + fixture repo trees + an in-memory SQLite database, driving `run_scan` with a recording `ScanReporter`. Possible only because `core` has no Tauri dependency (§3).

## 17. Performance

Against the PRD §11 targets:

| Target | Approach |
|--------|----------|
| Cold scan 50 repos < 60s | Rayon across repos; `tokei` and `git2` are both fast; the likely bottleneck is `tokei` on large trees, mitigated by the prune list (FR-1.4) which excludes `node_modules` and `target` — usually the bulk of the bytes |
| Warm re-scan < 10s | Fingerprint skip (§6.5) reduces this to git HEAD reads plus manifest hashing plus the always-run match step |
| Matching | Two-phase (§8.4); the SQL narrow with `idx_affected_ranges_pkg` reduces tens of thousands of advisories to a handful of candidates per dependency |
| Memory < 500MB | Streaming OSV ingest (FR-5.10); analyses are sent to the writer and dropped rather than accumulated; language stats stored as aggregates, never file lists |
| UI responsiveness | All long work off the main thread, progress via events, virtualized tables |

Deferred until measured: parallelism *within* a repo, a persistent scan daemon, mmap'd advisory index. At 10–50 repos these are speculative and would add real complexity.

## 18. Security and privacy

- **Outbound network is exactly two destinations**, both enumerable in the Tauri CSP and both user-visible: `storage.googleapis.com` / `api.osv.dev` (advisories), and package registries (only on the explicit FR-8 action).
- **Nothing about the user's code is transmitted.** OSV bulk downloads are one-way: the app downloads the whole ecosystem database and matches locally, so the user's dependency list never leaves the machine. This is a direct consequence of choosing bulk download over the query API, and is the main reason to prefer it.
- **The FR-5.9 live query is the one exception** — it sends a single package name and version. It is opt-in, per-dependency, and the UI says so.
- **Tauri capabilities are minimally scoped**: the `fs` plugin is granted only the app's own data and config directories. Reading scanned repositories happens in Rust, which is not subject to the frontend's capability restrictions — so the webview never holds filesystem access to the user's source, only the core does.
- **No secrets in phase 1.** Phase 2 API keys go to the OS credential store via `keyring` — never SQLite, never the config file (PRD H2).
- **Subprocess execution is not used anywhere.** No `npm`, no `cargo`, no `git` binary. All git access is in-process via libgit2. This eliminates the entire class of attacks where a scanned repository's config or hooks cause code execution during analysis — a real risk when scanning repositories you did not write.

The last point deserves emphasis: pointing a tool at arbitrary repositories and shelling out to package managers inside them is how a scanner becomes an execution vector. Reading files and git objects in-process avoids it structurally.

## 19. Build and packaging

- **Workspace**: root `Cargo.toml` with `crates/core` and `src-tauri` as members.
- **Bindings**: `tauri-specta` writes `src/bindings.ts` during the `src-tauri` build. CI fails if the generated file is dirty, preventing drift between Rust types and TypeScript.
- **CI** (GitHub Actions, matrix over `windows-latest` / `macos-latest` / `ubuntu-latest`): `cargo fmt --check`, `cargo clippy -D warnings`, `cargo test`, `tsc --noEmit`, `eslint`, then `tauri build`.
- **Installers** (M5): MSI + NSIS (Windows), DMG (macOS, universal binary), AppImage + deb (Linux).
- **Signing**: deferred past M5; unsigned builds will warn on Windows and macOS. Decide before any public distribution.
